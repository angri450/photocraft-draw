# 关于确定动作状态的思维链

## 关于这一层在流程里的位置

遮挡关系定的是谁挡住谁。动作状态定的是谁在使什么劲。这两件事有先后：

1. 先定动作。谁往哪个方向使劲，谁在压、谁在挑。
2. 再定位置。兵器在哪、身体在哪、谁挡谁。
3. 最后才定深度。层序和 z 值。

反过来做不成立。先摆位置再补动作，位置一旦摆定，动作就被位置锁死了，
想改也改不动。所以在写绘制方案之前，动作必须先想清楚。

## 关于为什么模型容易取平均值

模型写打斗场景时，方案里往往只有「谁有什么兵器」和「握在哪只手上」。
这两个信息不足以推出动作。两个人各有一件兵器，模型写出来的姿态
大概率是两边对称的：都举高、都朝中间、都往同一个方向使劲。

这个平均值在几何上完全成立，在现实里完全不可能。两个人同时从上往下压，
力量互相抵消，谁也没压住谁，画面读出来是两个人一起站着。
两个人同时往后撤，那是逃跑，不是打斗。

统计上取平均能让两边看起来平衡，现实中平衡只出现在还没开打的时候。

所以动作意图必须写进方案，不能指望从几何里推出来。

## 关于三个量

这一层要定三个量，三者的关系就是这一层要查的事。

### 意图向量

方案里每一层写一个 motion 字段：

```json
{
  "name": "wukong",
  "motion": {
    "action": "press_down",
    "angle": 65,
    "opponents": ["erlang shen"]
  }
}
```

angle 是画面坐标里的方向角。0 度朝右，90 度朝下，180 度朝左，270 度朝上。
两个交战角色的 angle 夹角接近 180 度，说明两人朝相反方向使劲，对抗成立。
夹角接近 0 度，说明两人朝同一侧使劲，对抗读不出来。

action 是受控词表里的词，每一层能用这些：

| 动作词 | 意思 | 方向范围 |
|---|---|---|
| press_down | 自上而下压 | 90 度上下 45 度 |
| lift_up | 自下而上挑 | 270 度上下 45 度 |
| push_out | 向外推 | 0 度上下 60 度 |
| pull_in | 向内拽 | 180 度上下 60 度 |
| sweep | 横扫 | 0 度上下 45 度 |
| thrust | 前刺 | 0 度上下 45 度 |
| parry | 格挡 | 0 度上下 60 度 |
| guard | 守势 | 90 度上下 90 度 |
| retreat | 后撤 | 180 度上下 60 度 |
| leap | 腾空 | 270 度上下 60 度 |
| stand | 站立不动 | 不限 |

方向角落在动作词要求的范围外，校验阶段就报错。所以先想清楚是压还是挑，
再填角度，不会填反。

### 骨段方向

从关节表直接算出来，不用手写。每一段骨骼一个方向向量，共十段：
躯干、头颈、左右上臂、左右小臂、左右大腿、左右小腿。

骨段方向不是用来算意图的，是用来查意图有没有落实。
手臂方向和意图向量反向是正常的：举过头顶准备劈砍，手臂必然朝上，
兵器才朝下。这是准备发力的姿势，不是拧着。

### 器物主轴

从兵器路径算出来，取最远点对当主轴。施力方向是持械者的手指向兵器远端
的方向，不是主轴的两端随便挑一个。

兵器层要写 holder，指明这层兵器归谁拿：

```json
{
  "name": "golden cudgel",
  "holder": "wukong"
}
```

## 关于三个关系

### 兵器主轴和意图向量

兵器施力方向和意图向量必须同向，夹角超过 50 度报「兵器拿反了」。
这一条最容易出问题：模型填了 press_down，兵器却画成横的，
或者兵器尖朝了另一个方向。

### 手和兵器

手要落在兵器上。手到兵器路径的距离超过 75 像素报「手没有握在兵器上」。

这一条查的是手悬在兵器旁边，不查手臂朝哪。举过头顶准备劈砍的姿势里，
手明明握着兵器，距离接近零，这一层不会报。
手臂方向和兵器主轴的夹角这个量在这里没有用：悟空劈砍时四段手臂与兵器
主轴夹角 91 到 169 度，全是正常姿势，拿它当判断标准会把对的姿势判成错的。

### 两个交战角色的意图向量

夹角小于 60 度报「两人朝同一侧使劲，对抗读不出来」。
这一条直接对应取平均值的错误，是这一层最要紧的检查。

## 关于投影和交叉角

这一层放在位置之后、深度之前。

### 引擎的投影到底做了什么

引擎的投影是仿射映射：画面横坐标等于 x 加上 z 乘 skew_x，纵坐标等于 y 减 z 乘 skew_y。
skew_x 默认 0.45，skew_y 默认 0.28，一个深度单位挪不到半个像素。

但这套偏移只对自带三维坐标的组件起作用，也就是 box3d_scene 和 rider3d。
custom_shape 和 figure_rig 没有 z，画出来的位置就是方案里写的二维坐标，一个像素都不动。
方案里的 depth 只决定谁压谁。

所以调深度改不了方向。两件直兵器在画面上是不是叠成一条线，
只能在画平面上设计。

### 为什么意图对了还不够

意图向量夹角够大，对抗才读得出来。可这一条管的是两个人的劲往哪使，
管不到两个人的兵器在画面上摆成什么形状。

大闹天宫续作贴身扭打那一格就是例子。意图夹角 180 度，看着完全对。
可两件兵器的施力方向差了 174 度，两条兵器线在画面上只差 6 度，
棒和兵器几乎叠成一条直线，画面读出来是两个人各自举着兵器站在一处。

这一条要在位置阶段解决。事后加检查，只能告诉人改好了。

### 交叉角

两个交战角色的兵器施力方向之间的锐角，就是画面上的交叉角。
交叉角低于 45 度报「画面上叠成一条线，读不出交错」。

设计的时候四件事一起定。

1. 交叉角。50 度到 75 度之间最好，太小读不出来，太大不像在格挡。
2. 交叉点落在两人之间的空档里，离任何人的肢体至少 45 像素。
   关节球和骨段有粗细，留 30 像素不够。
3. 交叉点离双方的握柄至少 80 像素。压在握柄上，四个关节球挤成一团，
   交叉点自己反而看不见。
4. 四条臂的长短搭配：上左、下右、下左、上右都要够长。
   短的那条缩成一个勾，整个 X 就散了。

手够不够得着同时要算。手臂长度按白模该有的比例：上臂 0.19 身高，
前臂 0.17 身高，手离肩最远 0.36 身高。够不着的手画出来是折断的。

这几件事互相牵制，交点一动，其余全动。拿尺子凑不出来，
写个脚本把这些量当设计变量去解，解完再照着解出来的坐标写关节表和兵器几何，
比自己拧位置可靠。贴身扭打那一格的 solve_layout.py 是一个可用的例子。

### 这一步在流程里的位置

1. 先定动作。谁往哪个方向使劲。
2. 再定位置。身体和兵器在画平面上的位置，交叉角、手臂长度、交叉点位置一起解。
3. 然后跑 motion 核对。交叉角、持械、意图三项在这一份报告里。
4. 最后定深度。哪件兵器压在交叉点上，由 depth 决定。

## 关于怎么想动作状态

想一个打斗场景，先问三个问题。

第一，谁主动。动手的那一方是攻方，另一个是守方还是避方。
这一问决定两个意图向量反向，不反向就是平均值。

第二，往哪个方向。攻方往对手身上压，对手往哪边让、往哪边顶，
是压、挑、推、拽、闪。方向角按这个填。

第三，兵器在哪。兵器从手里往哪个方向出去，就是施力方向，
意图向量跟它一致。兵器和手臂是同一件事的两头，手臂托着兵器，
兵器指哪，手臂就大致朝哪。手的位置要压在兵器身上，手悬在旁边就握不住。

这三问定了，写进方案的 motion 字段，再跑 `photocraft-draw motion` 核对。

## 关于命令

```sh
photocraft-draw motion plans/xxx.json
photocraft-draw motion plans/xxx.json --json out/motion.json
```

报告分四段。第一段是每个角色的动作声明和十段骨段方向，
第二段是兵器主轴和施力方向，第三段是交战方向的夹角，
第四段是动作提示。

提示为空，说明动作这一层自洽：兵器和意图同向，手握在兵器上，
两人朝相反方向使劲。

## 关于和白模的其他检查的关系

动作状态定的是谁在使什么劲，朝向定的是身体给观众看的这一面，
这是并列的两层，不是一件事。姿势定下来的时候，朝向一起定，写法见
[关于确定演出朝向的思维链](关于确定演出朝向的思维链.md)。

`motion` 读的是绘制方案，不读分层文件，所以出图之前就能跑。
`occlusion` 查谁挡谁，`contact` 查压在哪、兵器有没有从手背穿过去，
`depth` 查层序和三维坐标。四者查的是不同的东西，都要跑。

动作状态定得含糊，遮挡关系照样能算对，画面照样出得来，
但画出来的东西不对。所以这一层要在写方案的时候就过一遍。

## 关于一个容易犯的错

不要拿手的朝向当施力方向。手举在兵器后面，人往那边使劲，
兵器往另一边打，这是持械的正常姿势。手和兵器要分开看：

- 兵器主轴定方向。
- 手到兵器的距离定有没有握住。

一开始就搞混这一条，会把正常的举械姿势全判成错误，然后为了消掉提示
去改姿势，改完动作就不对了。
