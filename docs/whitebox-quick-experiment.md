# 白模快速出图实验记录

中间要确认位置关系和大致效果，不必先准备绘制方案。直接从命令目录查编号，拼一串原生绘制指令交给绘制服务，十三步耗时 3.2 秒出一张 1080×3600 的分层白模，十二个图层全是文字层、形状层、填充层和矢量智能对象，没有一张预先渲染的位图 [1]。这里省掉的只是中间稿那一段；白模确认之后要把素材、文字和组件组合成成品，绘制方案、构图组件和位图预处理一件都不能省，那是另一阶段的事。卡住项目的一直是调用方式。

## 实验是怎样搭起来的

实验脚本 `tools/quick_whitebox.py` 读取一份命令序列 JSON，开一个绘制服务会话，新建画布，然后逐条执行。序列里有两种条目：带 `id` 的走 `CommandBook.run`，也就是先去 `catalog.json` 校验编号存在，再交给 `engine.execute`；带 `method` 的走 `engine.call`，用来调用文档层的那些受路径约束的方法 [1]。整个过程中没有绘制方案、没有构图组件、没有 Python 绘图代码，也没有先把素材渲染成 PNG。

白模选的是前后几层位置关系：天空、远山、近山、地面四条色带压出前后，橙色椭圆是主体，底部黄色矩形是前景，中间置入一枚 SVG 徽章，四行文字标注各处名称。这些内容仅凭 `layer.newFillLayer.solidColor`、`shape.create`、`type.create` 和 `doc.place` 四条命令的不同参数就摆齐了 [1]。

## 实测得到的数据

1. 画布 1080×3600，命令 13 条，耗时 3.2 秒，出 PNG 76 KB、PSD 1.1 MB，十二个图层 [1]。
2. PSD 的图层构成是四个 Type、六个 Shape、一个 Fill、一个 Smart Object，文件头是 `8BPS`，没有位图图层 [1]。
3. 现有绘制方案示例 `plans/framework.json` 129 行、`plans/lengjing-grove.json` 149 行、`plans/spray.json` 443 行，准备方案还要先查找或者新增构图组件，这是项目目前出一张中间稿的前置成本 [2]。
4. `catalog.json` 收录 953 条命令、38 个类别，参数签名完整，其中 121 条的参数里带 `path` [2]。启动会话后查询 `engine.commands`，953 条里 728 条启用、225 条因为上下文不满足而禁用，比如没有选区、当前层不是文字层、文档没有时间轴 [1]。

## 两个阶段各自该用的手段

中间阶段只回答一件事：位置摆得对不对。谁在前谁在后、留多少边距、文字排在哪一行，核对完白模就改命令序列重新出一张，所以能省则省，绘制方案、构图组件和位图预处理都不必先动 [1]。

白模确认之后进入最终阶段，要把图片素材、文字和组件组合成可交付的成品，这一段的手续一件都不能省。位置和层序定下来之后，由绘制方案把它们固定成图层组；缺的结构就新增构图组件，登记进 `registry.py`；照片转绘、羽化、调色这类位图素材预处理该上就上；最后交给引擎输出 PSD，文字仍是文字层、形状仍是形状层，交付之后还能改 [2]。项目七步工作流管的是这一段，实验里的零方案入口只管前一段，两者不互相替代。

## 绕弯子的原因在哪里

第一处是会话模式把一批命令关在门外。项目的 `Engine` 通过 `photocraft-cli serve` 起常驻会话，这个模式会禁用带环境文件系统路径的命令。实验里直接调 `file.placeEmbedded` 报错：`automation command file.placeEmbedded uses ambient filesystem paths and is disabled; use capability-scoped document methods` [1]。加不加 `--automation-read-root` 和 `--automation-write-root` 都一样，启用与禁用的命令数都是 728 与 225，说明这是 serve 模式本身的规矩，不是路径白名单能解开的 [1]。而一次性执行模式 `photocraft-cli run` 没有这层限制，前几轮完成包装袋时一直能正常置入，于是遇到项目内跑不通就绕出去另外编写脚本，弯子就是这么绕出来的。

第二处是替代方法能力不全。改走 `doc.place` 之后，绝对路径一律被拒，相对路径还要求读取根覆盖到素材文件；把读取根设成工作区根、路径写成 `imgs/...` 才成功 [1]。但 `doc.place` 只接受 `path`、`x`、`y`、`scale`，实测给 `x` 和 `y` 之后置入位置仍然固定在画布中心，而命令目录里的 `file.placeEmbedded` 有 `center`、`fit`、`smartObject` 三个参数 [1][2]。AI 照着目录查到一条能力完整的命令，调下去失败，改用的替代方法又摆不到位，只能再想办法。

第三处是命令目录查不出会话里能不能跑。`engine.commands` 能逐条返回 `enabled` 和 `disabledReason`，但它标的是上下文相关的禁用，路径类命令要真正调用才报错 [1]。AI 事先查不到哪条会被拦，只能试错，这也加重了绕弯子。

第四处是文档把人往错路上带。README 的边界里写着「引擎单边渲染上限 1024 像素」，可同一份 README 的用法示例就输出 1600×900，这次实验又直接出了 1080×3600 [1][2]。技能说明 SKILL.md 里的引擎路径和项目路径写成了另一台机器上的 Windows 位置，跟分发时只有一个仓库的情况对不上，照着那份说明找不到文件 [2]。这两处过时信息会让 AI 判断项目设施不可用，转而绕开项目设施。

## 项目接下来该补哪几处

1. 把零方案直接出图提升为正式入口，只服务中间稿。实验脚本已经能读取命令序列出图，可以提升为 `photocraft-draw quick` 一类的子命令，AI 查完目录拼一个 JSON 就能出中间稿，不必先准备方案；这个入口不替代绘制方案主流程，最终成品仍按七步工作流走。
2. 给命令目录补会话可用性。生成目录时把「当前会话能否执行」「被禁用时改用哪个文档层方法」「路径要相对哪个根」一起收录进去，AI 一次查询就能定夺，不必逐条试。
3. 补齐文档层方法的能力。要么让 `doc.place` 支持定位，要么给 `Engine` 增加一次性执行模式，让 953 条命令在本机实验时全部可用，同时把两种模式的适用场合说明清楚。
4. 修正两处过时文档。README 的 1024 边界按实测改成说明渲染预览与正式出图的差别，SKILL.md 里写死本机路径改成写清楚引擎的查找顺序，不再出现任何一台机器的绝对路径。

这四件事互不依赖，改动的文件也不重叠，可以分头完成。四条都只针对出图链路的调用方式，最终组合阶段的绘制方案、构图组件和素材预处理保持原样。

## 这次实验留下的文件

实验脚本 `tools/quick_whitebox.py` 已随仓库收录，它读取一份命令序列，运行时生成一张 PNG 和一份分层 PSD。命令序列的结构写在 README 的中间稿章节里，产物落在输出目录，不随仓库分发。项目里长期留下的是 `quick` 子命令、`Engine.run_once` 一次性模式和命令目录的会话可用性标注。
